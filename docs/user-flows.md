# User Flows — канонические сценарии TicketBot

**Дата:** 2026-08-12
**Назначение:** единая основа для e2e-тестов и подключения новых фич. Каждый flow — это сквозной сценарий пользователя от входа до результата, с указанием роли, платформ, шагов и текущего статуса.

---

## Роли (терминология — CLAUDE.md, полная матрица — docs/roles-matrix.md)

| Роль | Кто | Ключевое |
|------|-----|----------|
| **Пользователь** | Посетитель | Покупает билеты, получает код/QR, предъявляет на входе. Минимальный ЛК. Стать организатором — через подписку. |
| **Организатор без группы** | Клиент с подпиской | Создаёт мероприятия, продаёт, проверяет билеты, статистика. Без площадки (Mini App). |
| **Организатор с группой** | Организатор + площадка | То же + подключённая площадка (TG-канал с подпиской или VK-группа). Бесшовный переход из «без группы». |
| **Супер-админ** | Владелец бота | `ADMIN_TELEGRAM_IDS`. Глобально управляет подписками пользователей и Telegram-каналов, пользователями, статистикой, рассылкой и здоровьем. Не получает прав на мероприятия и VK-группы организаторов. |

В матрице ниже TG/VK означают доступность сценария в соответствующем Mini App/web-контуре, если не указано иное; они не означают, что команды платформенного бота зарегистрированы. Telegram-бот сейчас в основном открывает Mini App, а VK/MAX боты содержат базовые пользовательские команды.

## Канонические сквозные сценарии (user journeys)

### 🧍 Пользователь — покупка и вход (F1→F2→F7)

```
Вход (TG Mini App / VK Mini App)
  → Найти мероприятие (лента / анонс)
  → Купить билет (платный/бесплатный)
  → Получить билет: код + QR в «Моих билетах», опционально ЛС
  → На входе предъявить код/QR организатору
  → (опц.) Отмена билета
```

**Ожидаемый результат:** билет виден в кабинете, код XXXX-XXXX предъявляется на входе.

### 🎪 Организатор — создание и продажа (F4→F5→F9→F7)

```
Вход (TG / VK, линковка F8 если кросс)
  → Подписка (F10: канал или пользователь)
  → Создать мероприятие (F4)
  → Подключить канал/VK-группу (F11/F12)
  → Опубликовать анонс (F5) + опц. продвижение (F6)
  → Создать промокод на скидку (F20: код, % или сумма, срок, лимит, вкл/выкл)
  → Покупатель вводит промокод при покупке → скидка в «Итого»
  → Задать цены по дате (F21: диапазоны с абсолютными датами, сплошное покрытие от публикации до даты)
  → Покупатель платит цену диапазона на дату покупки; цена фиксируется при покупке
  → Смотреть статистику (F9) + использованные промокоды
  → На входе: проверить код (F7) — ввести вручную или отсканировать QR (камера/фото, авто-check-in)
```

**Ожидаемый результат:** анонс в канале/группе, продажи в статистике, check-in по коду/QR.

### 🎛️ Супер-админ — управление платформой (F13→F14→F15→F16→F17)

```
Вход (TG)
  → Подписать канал (F13) + назначить админа (F14)
  → Глобальная статистика (F15)
  → Рассылка (F16) / Здоровье (F17)
```

**Ожидаемый результат:** каналы изолированы, админы назначены, мониторинг работает.

## Киллер-фича: кросс-платформенный цикл (F1 ↔ F7, обе стороны)

Одно мероприятие на всех площадках: код билета платформонезависим, check-in
по коду работает с любой площадки. Синхронизация счётчиков (sold/available)
мгновенная — общая БД.

### Направление A: купил в VK → проверил в TG (F1+VK → F7+TG)

```
VK-покупатель                     TG-организатор (канон)
    │                                   │
    │  F8 линковка TG↔VK ◄──────────────┘
    ▼                                   │
  F1 купить билет (VK Mini App)         │
    │                                   ▼
    ▼                                  F7 проверить код (TG)
  F2 билет: код + QR + ЛС VK            │
    └──────────────────────────────►  F9 статистика: продан = 1
```

**Реализовано:** `test_vk_e2e.test_full_vk_organizer_cycle` (купил в VK → проверил в TG).

### Направление B: купил в TG → проверил в VK (F1+TG → F7+VK) — симметрия

```
TG-покупатель (X-Skip-Auth)        VK-организатор (канон, линковка F8)
    │                                   │
  F1 купить билет (web, TG)             │
    │                                   ▼
    └──────────────────────────────►  F7 проверить код (VK Mini App)
```

**Реализовано:** `test_vk_e2e.test_tg_buy_vk_checkin_symmetry` (куплен в TG → validate/checkin в VK → 200).

### Синхронизация возврата: VK-возврат → TG-статистика (F3 + VK)

```
VK-покупатель                     TG-организатор (канон)
    │                                   │
  F1 купить билет (VK)                  │
    │                                   ▼
    │                                  F9 stats: sold=1, available-1
    │                                   │
  F3 возврат (VK, POST /tickets/{id}/cancel)
    │                                   ▼
    └──────────────────────────────►  F9 stats: sold=0, refunded=1, available вернулся
```

**Реализовано:** `test_vk_e2e.test_vk_buy_refund_sync_to_tg`.

## Как строить тесты и фичи на flows

### Правило
1. **Новая фича** должна вписываться в существующий flow (или создавать новый flow с обновлением матрицы).
2. **e2e-тест** = сквозной проход по flow (вход → шаги → ожидаемый результат).
3. Платформы тестируются симметрично: каждый flow для TG и VK, если платформа активна.

- ✅ **F2** (Мои билеты + QR) — `tests/test_web_api.py::TestCabinetFlow` (реальный PNG)

- ✅ **F5** (анонс) — TG-сим `tests/test_telegram_sim.py` (репост анонсов в канал)

- ✅ **F1+F3 синхронизация VK→TG** — `tests/test_vk_e2e.py::test_vk_buy_refund_sync_to_tg` (покупка/возврат в VK, статистика в TG)
- ✅ **F1+F7 симметрия TG→VK** — `tests/test_vk_e2e.py::test_tg_buy_vk_checkin_symmetry` (куплен в TG → check-in в VK)

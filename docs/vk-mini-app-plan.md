## 1. Концепция (зафиксирована)

Киллер-фича: **одно мероприятие живёт на всех площадках** (TG + VK), продажи ведёт организатор.

| Роль | Определение |
|------|-------------|
| **Суперадмин** | Владелец бота. Привязан к Telegram (`ADMIN_TELEGRAM_IDS`). VK-варианта нет. |
| **Организатор** | **Создатель мероприятия.** Не обязан владеть каналом или VK-группой. |
| **Пользователь** | Покупатель. Аккаунты на площадках раздельные (без линковки). |

**Ключевые принципы:**
1. Каналы TG и группы VK = **цели публикации**, не «точка владения». Организатор добавляет их сам, по необходимости.
2. **Линковка идентичности — только для организаторов.** Покупатели раздельные.
3. Одно мероприятие = одна запись `Event`. Продажи могут вести несколько людей (соработники).
4. Оплата — заглушка (как в TG, `payment=completed`). VK Pay — отдельной задачей.
5. **TG-код не изменяется.** Всё аддитивно; изменения shared core — только backward-compatible, помечены `[DECISION]`.

## 3. Архитектура: идентичность организатора

### Проблема
`User` = строка на `(platform, platform_user_id)` (`models.py:77-80`). Организатор на TG и VK — две записи → мероприятия/подписка/права разъехались.

### Решение: `user_identities`
```
user_identities(
    id, user_id FK -> users.id,
    platform, platform_user_id,
    UNIQUE(platform, platform_user_id)
)
```
- `users` остаётся «человеком». Все способы войти ведут к каноническому организатору.
- Миграция: наполнить `user_identities` из существующих `users` (одна строка на каждого).
- `get_or_create` → резолвит identity → канонический user.

### Линковка (только организаторы, по одноразовому коду)
1. Организатор в TG-кабинете: «Привязать VK» → показывается **одноразовый короткий код** (TTL ~10 мин).
2. В VK Mini App: «Привязать Telegram» → ввод кода → VK-identity связывается с TG-каноном.
3. Безопасность: обе стороны уже авторизованы своим протоколом (TG initData, VK sign). Слепой merge по имени/ID запрещён.
4. Для организатора-покупателя линковка не нужна — check-in и так по коду.

**`[DECISION]`** Резолвинг в `get_or_create` — правка `core/services.py` (shared core). Для TG backward-compatible: нелинкованные пользователи остаются каноном сами по себе. Но файл общий — требуется согласование до правки.

## 4. Архитектура: VK-группы и публикации (placements)

### Проблема
Сейчас `Event.channel_id` → анонс в один TG-канал (`announce.py`). Нужно «одно событие опубликовано в N целей».

### Решение: `event_publications`
```
event_publications(
    id, event_id FK,
    platform,          -- telegram | vk
    target_type,       -- telegram_channel | vk_group_wall | vk_group_message | vk_user_dm
    target_id,         -- tg channel id | vk group id | vk user id
    created_by, created_at, status, last_error
)
```
- `POST /admin/events/{id}/publish` принимает цель и создаёт публикацию; анонс постится в выбранную цель.
- `channel_id` остаётся «первичной» TG-целью (обратная совместимость с текущим publish).
- Самообслуживание: как TG-каналы (#142/#143), так и VK-группы организатор добавляет сам.

### VK-группа как модель
```
vk_groups(
    id, group_id (VK), title,
    community_token (зашифрованный),
    owner_user_id, created_at
)
```
- Подписка-изоляция VK-группе **не нужна**: организатор платит подписку на себя (`User.subscription_*`), группа — только цель рассылки. Это следствие новой концепции.
- Токен сообщества: Mini App через `VKWebAppGetCommunityToken` (группы, где пользователь админ и установлено приложение) → отправляет на бэкенд → храним зашифрованным → постим `wall.post` / `messages.send`.

**`[DECISION]`** Хранение community token: зашифрованный столбец + секрет в env. Точный API-контур и scope — проверить при внедрении (см. Нерешённые вопросы, №1).

## 5. Архитектура: соработники мероприятия

### Решение: `event_managers` (M2M)
```
event_managers(event_id FK, user_id FK)  -- PK (event_id, user_id)
```
- Расширение `_can_manage_event` (`routes.py:1296`): super-admin → owner → **manager** → channel-admin.
- Менеджер получает «вести продажи»: публикация, check-in, статы, билеты, пригласительные.
- Добавление менеджера — по платформенному ID (TG ID / VK ID) → резолвится в канонического организатора через `user_identities`. **Именно здесь линковка организаторов и даёт выгоду.**

**`[DECISION]`** Права менеджера: delete/subscription — только у owner. Менеджер — продажи и публикация. Уточнить при реализации.

## 6. Архитектура: VK-аутентификация и фронтенд

### Аутентификация (подтверждено механизмами VK)
- Mini App открывается с launch-параметрами `vk_*` + подпись `sign`.
- Валидация на сервере: HMAC-SHA256 секретным ключом приложения, base64url, constant-time сравнение — **прямой аналог `validate_init_data`** (`app/web/dependencies.py`).
- Готовая Python-либа для FastAPI: `vk-mini-app-auth` (без зависимостей).
- Результат: `vk_user_id` → канонический организатор (или создание нового User платформы `vk`).

### Фронтенд
- Текущий `app.js` почти платформонезависим (SPA на `fetch` + X-Init-Data).
- VK Mini App: `vk-app.html` (сейчас стаб) → детект VK Bridge → вместо `X-Init-Data` отправлять VK launch params (`Authorization`).

**`[DECISION]`** Переиспользовать `app.js` целиком (правка общего файла) или сделать отдельный VK-entry поверх общего API. Нерешённый вопрос №2.
